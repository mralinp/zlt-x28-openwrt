<h1 dir="rtl" align="right">مهندسی معکوس مودم‌های 5G مدل ZLT X28 و X28 PRO</h1>

<h2 dir="rtl" align="right">قسمت ششم: ساخت feed امضاشده؛ چطور opkg رو با سخت‌افزار آشتی دادیم؟</h2>

**نویسنده: علی نادری پاریزی — بازبینی: ۲۰۲۶-۱۱-۱۰**

یه روتر می‌تونه اینترنت بده و بازم نگهداریش سخت باشه. اگر برای هر قابلیت تازه مجبور باشیم چند فایل ko رو دستی کپی کنیم، package database رو دست‌کاری کنیم و ترتیب load رو از حفظ بدونیم، هنوز تجربه استاندارد OpenWrt رو نداریم. قدم بعدی پروژه این بود که همین کارها به بسته‌های قابل نصب، ارتقا و بررسی تبدیل بشن.

توی [قسمت قبل](05-sdk-kernel-and-drivers.md) درباره ساخت module حرف زدیم. اینجا مسئله متفاوتی داریم: چطور به opkg بگیم دستگاه واقعاً چه قابلیت‌هایی داره، کدوم بسته قابل نصبه و کدوم باید صریحاً رد بشه؟ نتیجه یه feed امضاشده مخصوص همین خانواده و Kernel هست، نه یه راه عمومی برای نصب هر kmod روی هر دستگاه ARM64.

<h2 dir="rtl" align="right">یه سوءتفاهم مهم: همه بسته‌های OpenWrt رو دوباره نساختیم</h2>

در نسخه مورد بررسی، userspace از OpenWrt 23.05.5 می‌آد. تعداد زیادی از بسته‌های عادی aarch64_generic از feed رسمی قابل استفاده‌ان. این به معنی تست تک‌تک اون‌ها نیست؛ یعنی مشکل وابستگی مستقیم به ABI همین Kernel رو ندارن. moduleهای رسمی اون release برای Kernel 5.15 ساخته شدن و با Kernel اختصاصی 4.19.205 ما یکی نیستن.

پس کار این نبود که کل مخزن OpenWrt رو دوباره کامپایل کنیم. بسته‌های مخصوص برد، moduleهای لازم و بعضی ابزارهای وابسته به backend vendor ساخته یا سازگار شدن؛ بسته‌های آماده‌ای که قابل استفاده بودن، آماده موندن. توی مستند ساخت باید این تفکیک روشن باشه، وگرنه خواننده تصور می‌کنه یه target کامل رسمی با همه اجزای بازسازی‌شده در اختیار داریم.

<h2 dir="rtl" align="right">feed چیه و package database چه چیزی می‌دونه؟</h2>

feed یه فهرست بسته‌ها به‌همراه فایل‌های ipk و اطلاعات لازم برای نصب اون‌هاست. opkg از روی نام، نسخه، معماری و dependency تصمیم می‌گیره چه چیزی نصب بشه. ولی خودش از وجود واقعی یه قابلیت داخل Kernel خبر نداره. اگر database با سخت‌افزار اختلاف داشته باشه، ممکنه برنامه قابل اجرا رد بشه یا چیزی نصب بشه که در عمل کار نمی‌کنه.

مثلاً برنامه‌ای به یه kmod وابسته‌ست، اما همون قابلیت از قبل داخل Kernel ساخته شده. نبود یه فایل ko جدا در این حالت به معنی نبود قابلیت نیست. برعکس، ساختن یه رکورد خالی برای قابلیتی که واقعاً وجود نداره، dependency رو ظاهراً حل می‌کنه ولی مشکل رو به زمان اجرا منتقل می‌کنه.

<div dir="rtl" align="center">

| نوع ورودی feed | چه چیزی همراهش هست؟ | چه چیزی رو ثابت نمی‌کنه؟ |
| ---: | ---: | ---: |
| رکورد kernel | هویت Kernel برای حل dependency | ساخت یا تعویض خود Kernel |
| stub | رکورد بسته برای قابلیت موجود | اضافه‌شدن قابلیت تازه به Kernel |
| بسته module واقعی | فایل ko، dependency و فهرست load | موفقیت همه workloadها |
| بسته x28-* | منطق مخصوص برد و اتصال به OpenWrt | حذف همه backendهای اختصاصی |
| بسته امضاشده | اصالت index و تطبیق فایل با آن | بی‌اشکال‌بودن کد یا سازگاری با هر دستگاه |

</div>

<h2 dir="rtl" align="right">سه جواب صادقانه به یه dependency</h2>

برای هر kmod، سه حالت داریم. یا قابلیت در همین Kernel و تصویر موجوده، یا باید module هماهنگ بسازیم، یا فعلاً نمی‌تونیم نیازش رو تأمین کنیم. feed هر سه حالت رو نمایش می‌ده. گروه سوم با خطای مشخص رد می‌شه؛ این شکست نصب، از موفقیت ظاهری یه بسته غیرقابل استفاده بهتره.

در snapshot مستند feed، از ۹۷۶ بسته kmod رسمی، ۲۰۸ مورد پوشش داده شدن: ۱۸۰ stub و ۲۸ بسته دارای module ساخته‌شده. این اعداد به تاریخ و index همین بررسی وابسته‌ان. در قسمت انتشار توضیح می‌دیم چرا باید نسخه و hash index رو هم کنار شمارش بسته‌ها نگه داریم؛ اضافه‌شدن یه بسته تازه لزوماً تعداد قابلیت‌های سخت‌افزاری رو یکی زیاد نمی‌کنه.

nftables مثال روشنیه. این Kernel قابلیت‌های لازم برای firewall4 رو نداره؛ نصب یه بسته userspace نمی‌تونه اون زیرساخت رو ایجاد کنه. بنابراین سیستم فعلاً fw3 و iptables-legacy داره. همین منطق درباره namespaceها یا بعضی subsystemهای غایب هم صادقه.

<h2 dir="rtl" align="right">چرا ipset هم استثنا شد؟</h2>

اسم یه subsystem لزوماً همه انواع و extensionهای اون رو توصیف نمی‌کنه. نسخه vendor از ipset یه subset مشخص داره. اگر dependency عمومی رو بی‌قید تأیید کنیم، برنامه‌ای که به نوع غایب نیاز داره بعداً خطا می‌ده. پروژه به همین دلیل بسته‌های vendor ipset و زنجیره وابستگی محدود خودش رو داره.

این موضوع در عیب‌یابی مهمه. وقتی یه برنامه می‌گه ساختن set شکست خورده، اول باید نوع set و revision پشتیبانی‌شده رو بررسی کنیم؛ نه اینکه چند بار همون ipk رو نصب کنیم. آزمون نصب package، آزمون ساخت set و آزمون عبور ترافیک هر کدوم شاهد جدا می‌خوان.

<h2 dir="rtl" align="right">نسخه بسته فقط یه برچسب تزئینی نیست</h2>

بسته‌های این feed از epoch برابر 1: استفاده می‌کنن تا نسخه مناسب دستگاه در مقایسه نسخه‌ها بر رکورد رسمی نامناسب اولویت بگیره. epoch رو با نسخه Kernel اشتباه نگیریم؛ این بخش از قرارداد package manager برای مرتب‌کردن نسخه‌هاست.

برای هر تغییر فایل، نسخه یا revision بسته هم باید تغییر کنه. وگرنه دو فایل متفاوت می‌تونن با یه نام و نسخه به دست کاربر برسن و opkg دلیلی برای upgrade نبینه. ابزار release_check پیش از انتشار، محتوای بسته‌های feed و bundle تصویر رو مقایسه می‌کنه و تغییر بی‌افزایش نسخه رو گزارش می‌ده.

گام مهم بعدی این بود که تصویر و feed از همون ipkها استفاده کنن. قبلاً ممکن بود یه script در تصویر دستی کپی بشه و نسخه feed اون عقب بمونه. حالا یه خروجی ساخته می‌شه و دو مصرف‌کننده داره. این کار مشکل نسخه‌ها رو حذف نمی‌کنه، اما نقطه اختلاف رو قابل بررسی می‌کنه.

<h2 dir="rtl" align="right">امضای feed از کجا اعتماد می‌سازه؟</h2>

کلید عمومی feed در تصویر قرار می‌گیره. کلید خصوصی برای امضا نگه داشته می‌شه و وارد روتر یا مخزن عمومی نمی‌شه. opkg امضای index رو بررسی می‌کنه و اطلاعات بسته‌ها و hash فایل‌ها از همون index می‌آد. اگر کسی فقط یه ipk رو عوض کنه، تطبیق با index باید شکست بخوره؛ اگر index رو عوض کنه، امضاش باید معتبر باشه.

این زنجیره جای بررسی source، dependency یا آزمون runtime رو نمی‌گیره. یه بسته معیوب هم ممکنه به‌درستی امضا شده باشه. امضا جواب «این خروجی از زنجیره انتشار مورد اعتماد اومده؟» رو می‌ده، نه «این تغییر هیچ باگی نداره؟». خاموش‌کردن کنترل امضا برای خلاص‌شدن از خطای نصب، همین مرز اعتماد رو حذف می‌کنه.

خط feed در snapshot فعلی مستندات اینه؛ این یه نمونه پیکربندی برای تصویر سازگاره، نه فرمان تغییر روتر:

<div dir="ltr">

<pre dir="ltr" align="left"><code dir="ltr" class="language-text">src/gz x28 https://github.com/mralinp/zlt-x28-openwrt/releases/latest/download</code></pre>

</div>

این URL به قرارداد انتشار پروژه وابسته‌ست. release مربوط به feed باید latest باقی بمونه و releaseهای فریمور جای اون رو نگیرن. برای همین، مفهوم «آخرین release» در این مخزن رو نمی‌شه بدون نگاه به workflow، همون جدیدترین فریمور فرض کرد.

<h2 dir="rtl" align="right">انتشار اتمی فقط اسم یه مرحله CI نیست</h2>

بسته‌ها اول روی release قرار می‌گیرن و index در آخر جایگزین می‌شه. این ترتیب احتمال رسیدن کاربر به فهرستی رو کم می‌کنه که هنوز فایل‌های لازم اون منتشر نشدن. نسخه‌های قدیمی هم تا زمان پاک‌سازی می‌تونن برای rollback باقی بمونن؛ ولی وجود فایل قدیمی، به‌تنهایی به معنی سازگاری اون با وضعیت جدید دستگاه نیست.

در آزمون ثبت‌شده، rollback یه بسته و برگشت به نسخه جدید روی دستگاه انجام شده. ماژول‌های boot-critical در همون آزمون downgrade نشدن. تعمیم اون نتیجه به تمام packageها درست نیست. ضمن اینکه opkg این تصویر نصب مستقیم از URL رو پشتیبانی نمی‌کنه؛ راه مستند، دریافت فایل، تطبیق hash و نصب فایل محلیه.

<h2 dir="rtl" align="right">ارتقای بسته با ارتقای فریمور فرق داره</h2>

دستور opkg upgrade فایل‌های packageها رو عوض می‌کنه. خودش یه تراکنش کامل A/B برای کل سیستم نیست. اگر یه daemon یا module از قبل در حافظه باشه، تغییر فایل لزوماً نسخه در حال اجرا رو عوض نمی‌کنه. بعضی تغییرها پس از reboot اثر می‌ذارن و همین reboot به boot counter مربوطه.

به همین دلیل، این مقاله دستور اجرای کورکورانه upgrade روی تنها مسیر اینترنت رو ارائه نمی‌ده. برای آموزش می‌تونیم اول موجودی رو بخونیم؛ این فرمان‌ها نصب یا ارتقا انجام نمی‌دن و خروجی از قبل ساخته‌شده‌ای هم برای اون‌ها جعل نشده:

<div dir="ltr">

<pre dir="ltr" align="left"><code dir="ltr" class="language-sh">opkg list-installed
opkg list-upgradable
/etc/init.d/x28-kmods modules</code></pre>

</div>

در ثبت آزمون‌های ۴۵ تا ۵۰، بررسی امضا، ارتقای moduleهای دستی به packageهای واقعی، load پس از reboot و بسته‌بندی مشترک تصویر و feed جداگانه بررسی شدن. دامنه این شواهد رو همون‌قدر گزارش می‌کنیم؛ نه سازگاری کامل همه بسته‌های رسمی.

حالا feed قابل نگهداری‌تر شده، اما هنوز یه سؤال داریم: آیا همون تصویر روی X28 PRO هم با همون رفتار کار می‌کنه؟ [قسمت هفتم](07-x28-and-pro-hardware-support.md) درباره فاصله بین «روی دستگاه من کار کرد» و «از یه خانواده دستگاه پشتیبانی می‌کنیم» هست.
