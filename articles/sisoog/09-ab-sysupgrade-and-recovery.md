<h1 dir="rtl" align="right">مهندسی معکوس مودم‌های 5G مدل ZLT X28 و X28 PRO</h1>

<h2 dir="rtl" align="right">قسمت نهم: ارتقای A/B؛ اول تصویر رو بنویس، بعد مسیر بوت رو عوض کن</h2>

**نویسنده: علی نادری پاریزی — بازبینی: ۲۰۲۶-۱۱-۱۰**

وقتی از بیرون به یه روتر نگاه می‌کنیم، ارتقا ظاهراً یه دکمه‌ست: فایل رو انتخاب می‌کنیم، چند دقیقه صبر می‌کنیم و دستگاه برمی‌گرده. از داخل، همون چند دقیقه مجموعه‌ای از تصمیم‌های حساسه. فایل پذیرفته شده؟ target درست انتخاب شده؟ نوشتن کامل شده؟ بعد از reboot کدوم نسخه اجرا می‌شه؟ این قسمت درباره تبدیل اون دکمه به یه workflow قابل توضیحه.

در این پروژه، NAND از قبل پارتیشن‌های A و B داره، ولی وجود دو کپی به معنی داشتن یه upgrade امن آماده نیست. بخشی از منطق vendor برای همگام‌کردن تصویرها نوشته شده و ممکنه نسخه آزمایشی ما رو بازنویسی کنه. باید اول رفتار موجود رو می‌فهمیدیم و بعد تصمیم می‌گرفتیم کدوم بخش رو نگه داریم.

<h2 dir="rtl" align="right">A/B یعنی دو جای بوت؛ نه دو دستگاه مستقل</h2>

بعضی اجزای firmware نسخه A و B دارن، ولی داده‌های دیگه مشترکن. misc انتخاب بوت و وضعیت slotها رو نگه می‌داره. داده‌های NV و بعضی تنظیم‌ها هم مستقل از تصویر سیستم‌عامل هستن. overlay پروژه می‌تونه روی user_data قرار بگیره و با عوض‌شدن UUID تصویر تازه بشه.

پس برگشت به slot قبلی لزوماً همه وضعیت دستگاه رو به گذشته برنمی‌گردونه. اگر تنظیم مشترک تغییر کرده باشه یا overlay دوباره ساخته بشه، باید اثرش جدا بررسی بشه. عبارت «rollback» بدون مشخص‌کردن اینکه درباره image، config یا هر دو حرف می‌زنیم ناقصه.

<div dir="rtl" align="center">

| بخش | نقش | اشتباه رایج |
| ---: | ---: | ---: |
| rootfs_a و rootfs_b | دو جای تصویر سیستم | فرض اینکه همیشه یکی stock باقی می‌مونه |
| misc | اولویت و وضعیت انتخاب بوت | تغییر انتخاب پیش از verify تصویر |
| x28-bootok | رسیدن سیستم بوت‌شده به نقطه سلامت و reset tries | یکی دانستن tries صفر با success ثبت‌شده |
| overlay مشترک | فایل‌های قابل نوشتن و تنظیم‌ها | فرض حفظ خودکار تنظیم در هر تصویر |
| backup خارجی | راه برگشت به وضعیت ذخیره‌شده | یکی دانستن backup با Recovery آزموده‌شده |

</div>

<h2 dir="rtl" align="right">سیاست فعلی: همیشه slot غیرجاری</h2>

در کد فعلی platform.sh، اگر از A اجرا بشیم target برابر B و اگر از B اجرا بشیم target برابر A هست. همین انتخاب باید پیش از ورود به محیط RAM ثبت بشه و مراحل بعدی از همون تصمیم استفاده کنن. انتخاب هدف از روی حدس، نام فایل یا یه marker ناپیدا در محیط دوم قابل اتکا نیست.

این سیاست با برخی نسخه‌های تاریخی تفاوت داره. در تست‌های اولیه، upgrade درجا روی A انجام می‌شد و برای نوشتن B markerهای جدا وجود داشت. تا نسخه‌های مشخصی، script جاری دستگاه هنوز همون رفتار قدیمی رو داشت. بنابراین نصب یه package تازه در فایل تصویر آینده، رفتار upgrader نسخه فعلی رو عوض نمی‌کنه؛ مرحله ارتقا از کدی استفاده می‌کنه که همین حالا روی دستگاه اجرا می‌شه.

این یکی از مهم‌ترین نکته‌های آموزشی این مرحله‌ست: باید هم نسخه مقصد رو بشناسیم، هم نسخه مبدأ رو. اینکه کد main امروز درست target انتخاب می‌کنه، به معنی درست‌بودن کد موجود روی یه دستگاه قدیمی نیست.

<h2 dir="rtl" align="right">چهار مرحله‌ای که ترتیبشون اصل طراحی بود</h2>

اول فایل و board و وضعیت فعلی بررسی می‌شن. بعد target از RAM نوشته می‌شه. سپس محتوای نوشته‌شده بازخوانی و با محتوای مورد انتظار مقایسه می‌شه. فقط وقتی این مراحل موفق بودن، اولویت بوت تغییر می‌کنه. اگر write یا verify شکست خورد، misc نباید برای بوت تصویر ناقص تغییر کنه.

<div dir="ltr">

<pre dir="ltr" align="left"><code dir="ltr" class="language-text">check image + board + current state
    -&gt; select inactive slot
    -&gt; write target from RAM
    -&gt; verify logical filesystem content
    -&gt; update boot selection
    -&gt; reboot and check boot health</code></pre>

</div>

این نمودار، مدل رفتار کده؛ خروجی یه نشست واقعی نیست. برای بررسی سخت‌افزاری باید لاگ مراحل و hashهای مربوط به همون تصویر ثبت بشن. عدد صفر خروجی یه command هم نباید جای read-back کامل رو بگیره.

<h2 dir="rtl" align="right">چرا نوشتن از RAM؟</h2>

وقتی فایل‌سیستم هدف در حال استفاده باشه، بازنویسی اون می‌تونه برنامه و داده مورد نیاز همون عملیات رو از زیر پاش بکشه. OpenWrt برای upgrade مرحله دوم و RAM root داره. ابزارها و فایل‌های لازم باید پیش از کناررفتن محیط اصلی منتقل بشن؛ برنامه‌ای که بعد از pivot غایب باشه، با فرض قبلی اجرا نمی‌شه.

پروژه همین‌جا چند خطای واقعی داشت. یه بار stage2 در تصویر نبود. یه بار log روی overlay نوشته می‌شد، در حالی که همون مرحله overlay رو unmount می‌کرد. یه بار verify منتظر node دستگاه UBI بود که در RAM root خودکار ساخته نمی‌شد. این‌ها شکست منطق رمزنگاری یا خراب‌بودن NAND نبودن؛ نقص محیط اجرای عملیات بودن.

در مقاله آموزشی، این شکست‌ها ارزش دارن چون نشان می‌دن چرا یه command که در shell عادی کار می‌کنه، لزوماً در stage2 درست اجرا نمی‌شه. هر مرحله باید فقط روی چیزهایی تکیه کنه که وجودشون در همون محیط تضمین شده.

<h2 dir="rtl" align="right">hash کل پارتیشن همیشه معیار درستی نیست</h2>

ubiformat می‌تونه erase counterهای UBI رو تغییر بده. در نتیجه byteهای کل MTD بعد از نوشتن، الزاماً با فایل ورودی برابر نیستن، حتی وقتی محتوای منطقی فایل‌سیستم درست نوشته شده. به همین دلیل، verify باید بدونه چه لایه‌ای رو مقایسه می‌کنه.

در طراحی فعلی، attach و بررسی محتوای volume جای انتظار برابری خام همه byteها رو می‌گیره. metadata داخل بسته، hash و طول SquashFS مورد انتظار رو هم نگه می‌داره. این به معنی نادیده‌گرفتن headerها نیست؛ یعنی check فایل ورودی، check هندسه و check محتوای نوشته‌شده هرکدوم وظیفه خودش رو دارن.

این تفاوت برای NAND مهمه. یه فایل dump خام، تصویر UBI و tarball مخصوص sysupgrade سه قالب قابل جایگزینی با هم نیستن. اینکه هر سه پسوند bin یا tar داشته باشن، مجوز فرستادنشون به یه writer دلخواه نمی‌ده.

<h2 dir="rtl" align="right">misc؛ چند کپی، چند تصمیم حساس</h2>

رکورد انتخاب بوت در چهار کپی قرار داره. کد با شناخت magic و layout، byteهای مربوط به هدف رو تغییر می‌ده و کپی‌ها رو از آخر به اول می‌نویسه. بعد از هر گام، کل misc با وضعیت مورد انتظار مقایسه می‌شه. این ترتیب بر اساس تحلیل رفتار خواندن preloader انتخاب شده.

توی مسیر USB، block write به misc بارها ACK معتبر نگرفته؛ از موفقیت نوشتن rootfs نمی‌شه نوشتن misc رو نتیجه گرفت. مسیر مستند تغییر رکورد، ابزار stock به اسم dd-nand در سیستم در حال اجراست. به همین دلیل، مقاله یه دستور عمومی dd یا erase برای انتخاب slot ارائه نمی‌ده.

اگر کپی‌ها مختلف باشن، انتخاب اولین کپی معتبر و خرابی حین نوشتن اهمیت پیدا می‌کنه. تحلیل باینری درباره رفتار مورد انتظار کمک می‌کنه، اما تا آزمون قطع برق انجام نشده نباید بنویسیم این طراحی در هر لحظه قطع برق تضمین‌شده بازیابی می‌شه.

<h2 dir="rtl" align="right">tries، success و سلامت سیستم یکی نیستن</h2>

preloader شمارنده تلاش بوت داره. x28-bootok بعد از رسیدن به نقطه مناسب، tries مربوط به slot جاری رو صفر می‌کنه. تنظیم success و مسیر sync در firmware اصلی داستان جداگانه‌ای دارن؛ پروژه در برخی مراحل عمداً success رو به سبک vendor تأیید نمی‌کرد تا رفتار repair یا کپی روی slot دیگه اتفاق نیفته.

در تحلیل جدید، شاخه‌ای برای تغییر slot پس از رسیدن tries به شش دیده شده. اما مشاهده و تحلیل دو سطح شاهد متفاوتن. تست کامل fallback میان دو تصویر native که یکی عمداً بوت نمی‌شه هنوز در محدودیت‌های سند هست. reset شدن counter در بوت سالم رو نباید اثبات recovery بعد از هر crash معرفی کنیم.

<h2 dir="rtl" align="right">چه چیزی واقعاً روی دستگاه انجام شده؟</h2>

آزمون ۵۲ اول روی NAND شبیه‌سازی‌شده در QEMU اجرا شد و ۱۶ بررسی گذشت. اونجا رفتار write و verify و دست‌نخوردن misc پس از write ناموفق بررسی شد؛ ولی ابزار dd-nand vendor و Kernel واقعی دستگاه در همون تست حاضر نبودن.

بعد، تست ۵۳ روی دستگاه واقعی با تصویر یکسان انجام شد. در ۵۳b تصویر دارای یه فایل marker تازه نوشته شد و وجود همون فایل بعد از بوت بررسی شد. در ۵۳c نوشتن B و بوت native از B ثبت شد. در ۵۳d هم پذیرش تصویر امضاشده، رد تصویر نامعتبر و چرخه واقعی A به B و برگشت به A دیده شد.

این مراحل رو نباید به یه جمله «OTA کاملاً تست شد» خلاصه کنیم. تصویر تغییرکرده تست شده و تصویر امضاشده هم تست شده، ولی ترکیب تمام تغییرها، همه مبدأها و همه خرابی‌ها یه آزمون مستقل می‌خواد. ضمن اینکه بخشی از آزمایش‌ها پیش از سیاست جدید «همیشه slot غیرجاری» بودن.

<h2 dir="rtl" align="right">اولین upgrade ممکنه stock B رو حذف کنه</h2>

وقتی native روی A و firmware اصلی روی B باشه، هدف غیرجاری B هست. نوشتن native روی B یعنی نسخه stock داخلی رو از دست می‌دیم. پس بعد از این مرحله، دیگه درست نیست به کاربر بگیم «B همیشه recovery اصلیه». backup بیرونی و مسیر فلشر اهمیت بیشتری پیدا می‌کنن.

این معامله باید در متن انتشار روشن باشه. دو slot native می‌تونن برای برگشت نسخه مفید باشن، ولی یه محیط rescue مستقل با توان بازگرداندن stock نیستن. همچنین داده‌های مشترک و تازه‌شدن overlay با UUID متفاوت می‌تونن اثر متفاوتی روی هر بوت بذارن.

<h2 dir="rtl" align="right">خبر نسخه تازه در LuCI و ابزار x28-upgrade</h2>

در کد فعلی، لایه دریافت نسخه هم اضافه شده: x28-update-check نسخه جاری رو از /etc/x28-release می‌خونه، assetهای release رو بررسی می‌کنه و نتیجه رو موقتاً cache می‌کنه. اسم فایل بدون پسوند unsigned در انتخاب نسخه دخالت داره، ولی اسم فایل خودش اثبات امضا نیست. تصمیم نهایی اصالت هنوز با sysupgrade و ucert هست.

برای همین، ابزار x28-upgrade دو رفتار جدا داره. بدون آرگومان فقط نسخه رو بررسی می‌کنه؛ درخواست شبکه و نوشتن cache در /tmp ممکنه انجام بشه، اما تصویر رو فلش نمی‌کنه. این مثال فقط برای تصویر دارای همین package هست و اینجا اجرا نشده:

<div dir="ltr">

<pre dir="ltr" align="left"><code dir="ltr" class="language-sh">x28-upgrade</code></pre>

</div>

حالت تأییدشده ابزار، که در header source با -y معرفی شده، تصویر رو می‌گیره، SHA-256 فایل دریافت‌شده رو مقایسه می‌کنه، sysupgrade -T رو اجرا می‌کنه و بعد به sysupgrade -n می‌رسه. یعنی config حفظ نمی‌شه و reboot جزو عملیات هست. دکمه LuCI هم ابتدا همین اثرها رو در پنجره تأیید توضیح می‌ده و بعد کار رو در پس‌زمینه شروع می‌کنه. این بخش توضیح interface هست، نه درخواست اجرای اون روی دستگاه خواننده.

پیش از دانلود، script وضعیت tries، target و حافظه آزاد /tmp رو بررسی می‌کنه؛ برای تصویر و بازکردن اون در stage2 جا لازمه. lock هم جلوی شروع هم‌زمان دو upgrade رو می‌گیره. checksum فایل دانلودشده، کنترل امضای sysupgrade رو حذف نمی‌کنه؛ هر دو باید از مسیر خودشون عبور کنن.

در tests/test_update.sh مسیرها با fetcher و sysupgrade جعلی بررسی می‌شن؛ این یه تست host بدون شبکه و بدون دستگاهه. در وضعیت ۱۰ نوامبر، برای helper و دکمه LuCI هنوز رکورد آزمون سرتاسری روی واحد واقعی ثبت نشده. پس می‌تونیم بگیم رابط ارتقای شبکه‌ای پیاده شده، اما نمی‌گیم به‌روزرسانی بی‌حضور کاربر با تحمل همه خطاها آماده‌ست. خود source هم صریح می‌گه ابزار خودبه‌خود اجرا نمی‌شه.

<h2 dir="rtl" align="right">OTA هنوز یه لایه دیگه‌ست</h2>

sysupgrade موتور بررسی و اعمال تصویره. OTA یا ارتقا از راه شبکه، علاوه بر اون به پیدا کردن نسخه، انتخاب artifact مناسب، دریافت قابل اعتماد، سیاست زمان‌بندی و اطلاع‌رسانی نیاز داره. ساخت خودکار release در GitHub هم به‌خودی‌خود روتر رو خودکار ارتقا نمی‌ده.

تا وقتی مسیر بدون حضور کاربر، آزمون مدل‌ها و سناریوهای شکست ثبت نشده، این قسمت رو «زیرساخت ارتقای A/B» معرفی می‌کنیم، نه به‌روزرسانی خودکار بی‌نیاز از مراقبت. برای حرکت از آزمایش مهندسی به انتشار قابل اتکا، [قسمت دهم](10-release-engineering-and-next-steps.md) رو به همین قرارداد خروجی و نگهداری اختصاص دادیم.
