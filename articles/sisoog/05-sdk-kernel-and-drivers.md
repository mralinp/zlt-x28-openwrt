<h1 dir="rtl" align="right">مهندسی معکوس مودم‌های 5G مدل ZLT X28 و X28 PRO</h1>

<h2 dir="rtl" align="right">قسمت پنجم: از SDK تا درایور؛ چرا کامپایل موفق پایان کار نیست؟</h2>

**نویسنده: علی نادری پاریزی — بازبینی: ۲۰۲۶-۱۱-۱۰**

تا اینجای مجموعه، یه دستگاه بسته رو بررسی کردیم، به سیستمش دسترسی گرفتیم و OpenWrt رو با اینترنت سلولی بالا آوردیم. ولی برای ادامه کار، کپی‌کردن چند فایل کافی نبود. یه قابلیت جدید ممکن بود ابزار userspace بخواد، یه ماژول Kernel بخواد یا اصلاً به بخشی از سخت‌افزار مربوط باشه که هنوز قراردادش رو نمی‌شناسیم. این قسمت درباره تشخیص همین مرزهاست: چه چیزی رو دوباره ساختیم، چه چیزی رو نگه داشتیم و چطور فهمیدیم خروجی واقعاً قابل استفاده‌ست.

قبل از ادامه، **از Tozed بابت در اختیار گذاشتن SDK ممنونم.** این دسترسی برای فهمیدن اجزای پلتفرم و ادامه توسعه ارزشمند بود. این تشکر به معنی تأیید رسمی فریمور ما یا انتشار عمومی همه فایل‌های SDK نیست؛ این مجموعه تجربه توسعه مستقل ما رو روایت می‌کنه.

<h2 dir="rtl" align="right">SDK دقیقاً چه کمکی می‌کنه؟</h2>

SDK یا Software Development Kit مجموعه‌ای از ابزار و ورودی‌های ساخت برای یه پلتفرمه. ممکنه toolchain، فایل‌های پیکربندی Kernel، headerها، patchها، source بعضی درایورها و برنامه‌های آماده داشته باشه. وجود یه پوشه با اسم SDK به‌تنهایی تضمین نمی‌کنه همه اجزای دستگاه از source قابل ساخت باشن. برای هر جزء باید جدا ببینیم چه ورودی‌ای داریم و خروجی با کدوم نسخه فریمور هماهنگه.

تو این پروژه، SDK رو نباید با SDK عمومی OpenWrt یکی گرفت. SDK عمومی برای ساخت بسته‌های یه target مشخص مفیده؛ درخت vendor اطلاعات لازم درباره تغییرهای همین پلتفرم رو داره. حتی وقتی هر دو خروجی ARM64 می‌دن، الزاماً یه قرارداد Kernel یا کتابخانه ندارن. از طرف دیگه ImageBuilder معمولاً بسته‌های از قبل ساخته‌شده رو داخل تصویر می‌چینه؛ این کار به معنی کامپایل دوباره همه بسته‌ها نیست.

برای اینکه روایت پروژه دقیق بمونه، سه کار رو از هم جدا می‌کنیم: مونتاژ RootFS با بسته‌های آماده، بازکامپایل بسته‌های userspace در موارد لازم، و ساخت ماژول‌های هماهنگ با Kernel دستگاه. این‌ها هر سه بخشی از توسعه فریمورن، ولی مسئله و روش آزمونشون فرق می‌کنه.

<h2 dir="rtl" align="right">دو دنیا روی یه برد: OpenWrt جدید و Kernel قدیمی</h2>

پایه فعلی، userspace نسخه 23.05.5 روی Linux اختصاصی 4.19.205 هست. userspace شامل چیزهایی مثل UCI، netifd، dnsmasq و LuCI می‌شه. Kernel وظیفه مدیریت حافظه، شبکه و سخت‌افزار رو داره. این جداسازی کمک کرد ابزارهای استاندارد OpenWrt رو داشته باشیم و هم‌زمان مسیر کارکرده مودم و Wi-Fi رو حفظ کنیم.

این ترکیب به معنی پشتیبانی رسمی OpenWrt از MT6890 نیست. درایورهای vendor و قراردادهای داخلی مودم هنوز بخشی از تصویرن. «native» توی این پروژه یعنی RootFS خودمون بوت می‌شه و شبکه رو OpenWrt مدیریت می‌کنه؛ نه اینکه همه قطعات با درایور mainline جایگزین شده باشن.

<h2 dir="rtl" align="right">ABI؛ چرا یه فایل ko هم‌نام ممکنه کار نکنه؟</h2>

ABI قرارداد باینری بین دو جزءه. برنامه userspace معمولاً با syscall و کتابخانه‌ها حرف می‌زنه، اما ماژول Kernel مستقیم به symbolها و ساختارهای داخلی Kernel وابسته‌ست. یه ماژول ممکنه برای ARM64 ساخته شده باشه، اسم درستی داشته باشه و بازم روی این Kernel load نشه.

نسخه compiler، config، patchهای vendor و شکل export شدن symbolها مهمن. این Kernel از CONFIG_MODVERSIONS استفاده می‌کنه؛ اطلاعات نسخه symbolها هم وارد ماجرا می‌شه. صرفاً عوض‌کردن vermagic یا ردکردن کنترل نسخه، همون ساختارهای حافظه رو سازگار نمی‌کنه. در گزارش ساخت باید بگیم کدوم کنترل‌ها برقرار بودن و چه آزمون واقعی‌ای بعد از load انجام شده.

برای همین، «کامپایل شد»، «load شد» و «ترافیک واقعی رو عبور داد» سه نتیجه جدا هستن. WireGuard با ساخت module شروع شد، اما تست رابط، مسیر شبکه و ترافیک لازم داشت. ماژول TPROXY هم وقتی ارزش داشت که برنامه بتونه socket شفاف بسازه و بسته LAN واقعاً از اون مسیر عبور کنه.

<h2 dir="rtl" align="right">از dependency شروع کردیم، نه از فهرست آرزوها</h2>

به‌جای ساختن هر ماژولی که اسمش جالب بود، اول نیاز مصرف‌کننده رو دیدیم. WireGuard ماژول خودش رو لازم داشت. Passwall2 به مسیر TPROXY و socket نیاز داشت. بعضی برنامه‌های مدیریت ترافیک به scheduler یا action خاصی وابسته بودن. بعد مشخص کردیم کدوم قابلیت در Kernel هست، کدوم فایل vendor موجوده و کدوم رو واقعاً باید بسازیم.

منابع یه‌دست نیستن. WireGuard از wireguard-linux-compat اومده؛ فایل‌های TPROXY از Linux 4.19.205 گرفته شدن؛ بعضی بخش‌های crypto به تغییرهای SDK وابسته‌ان. اینکه همه رو با یه عنوان «درایورهای کامپایل‌شده OpenWrt 23» معرفی کنیم، این تفاوت مهم رو پنهان می‌کنه. بسته‌بندی برای OpenWrt 23 انجام می‌شه، اما ماژول باید با Kernel 4.19.205 سازگار باشه.

در یه مورد، symbolهای lookup مربوط به UDP از Kernel export نشده بودن. پروژه برای این نیاز یه helper مشخص به اسم x28_udp_lookup داره. این یه تغییر محدود برای یه dependency مشخصه، نه مجوزی برای export کردن هر تابع داخلی Kernel. هر وابستگی تازه، دامنه آزمون و نگهداری تازه‌ای هم می‌آره.

<h2 dir="rtl" align="right">یه خطای USB که ثابت کرد اسم نسخه کافی نیست</h2>

یکی از مثال‌های تازه، USB NCM بود؛ پروتکلی که می‌تونه دستگاه رو از طریق USB به کارت شبکه تبدیل کنه. در آزمایش ثبت‌شده، ماژول اولیه Kernel رو panic کرد. مسیر vendor در u_ether قبل از بررسی NULL به بسته دسترسی داشت، ولی timer مربوط به NCM می‌تونست ndo_start_xmit رو با ورودی NULL فراخوانی کنه.

اینجا هم‌نسخه‌بودن source به‌تنهایی مشکل رو حل نکرد. باید قرارداد بین دو بخش بررسی می‌شد. اصلاح ثبت‌شده، ارسال bundle بدون flush timer بود. بعد از اون، Mac کارت شبکه USB رو شناخت و ۲۰۰ ping با اندازه ۱۴۰۰ بایت پاسخ گرفت. این نتیجه، تست همون مسیر روی دستگاه آزمایشیه؛ benchmark سرعت USB یا پشتیبانی عمومی از هر hub نیست.

این تجربه یه درس کاربردی داره: وقتی crash توی مرز دو جزء رخ می‌ده، فقط به تابعی که آخرین بار اجرا شده نگاه نکنیم. چه کسی مجازه NULL بده؟ چه کسی مالک buffer هست؟ آیا callback از context مورد انتظار صدا زده شده؟ این سؤال‌ها از عوض‌کردن بی‌دلیل flagهای compiler مفیدترن.

<h2 dir="rtl" align="right">load کردن ماژول هم بخشی از طراحی بوت شد</h2>

اگر یه module خراب درست اول بوت load بشه، ممکنه قبل از رسیدن به SSH دستگاه رو از دست بدیم. پروژه ماژول‌های افزوده رو در مسیر جداگانه /lib/modules/x28 نگه می‌داره و loader بعد از رسیدن بوت به نقطه مناسب اون‌ها رو بارگذاری می‌کنه. هر بسته فهرست moduleهای خودش رو همراه داره؛ ترتیب load هم از dependencyها پیروی می‌کنه.

loader برای تلاش‌های ناتمام محدودیت داره. این محافظ، اثبات بی‌خطر بودن module نیست؛ فقط کمک می‌کنه یه شکست تکراری به بوت‌لوپ بی‌انتها تبدیل نشه. بعد از crash هم حذف marker بدون بررسی لاگ، عملاً درخواست تکرار همون آزمایشه.

روی تصویر نصب‌شده سازگار، این فرمان صرفاً فهرست بارگذاری رو نشون می‌ده؛ خودش دستور فلش یا تغییر slot نیست:

برای مرور شواهد، inventory قبل و بعد از load، پیام‌های Kernel و آزمون مصرف‌کننده رو کنار هم می‌ذاریم. نبود unknown symbol خوبه، ولی به‌تنهایی ثابت نمی‌کنه همه حالت‌های کارکرد درسته. برای درایور سخت‌افزاری باید خود سخت‌افزار مربوط هم در آزمون حاضر باشه.

<h2 dir="rtl" align="right">از خروجی آزمایشگاهی تا بسته قابل نگهداری</h2>

ماژول ساخته‌شده نباید برای همیشه یه فایل دستی روی روتر بمونه. نسخه، dependency، محل نصب، فهرست load و روش rollback باید مشخص باشه. تبدیل moduleها به ipk کمک کرد تصویر و feed از یه خروجی واحد استفاده کنن و دیگه دو نسخه متفاوت از یه قابلیت نگه نداریم.

در ثبت آزمون ۴۶، loader همه ۵۱ ماژول فهرست خودش رو بعد از بوت بارگذاری کرده. عدد ۵۱ اینجا تعداد moduleهای اون فهرسته؛ با ۵۱ پارتیشن NAND یا تعداد کل moduleهای Kernel یکی نیست. همین دقت ساده جلوی خیلی از برداشت‌های اشتباه در گزارش فنی رو می‌گیره.

دسترسی به SDK ادامه این کار رو ممکن‌تر می‌کنه، اما راه نگهداری بلندمدت همچنان بازه: کم‌کردن وابستگی به کد اختصاصی، ثبت patchهای محدود و آزمون روی هر دو مدل. در [قسمت ششم](06-signed-feed-and-packages.md) همین خروجی‌ها رو از دید opkg دنبال می‌کنیم؛ جایی که dependency درست به‌اندازه فایل باینری درست اهمیت داره.
