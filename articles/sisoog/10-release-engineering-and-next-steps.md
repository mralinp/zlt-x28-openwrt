<h1 dir="rtl" align="right">مهندسی معکوس مودم‌های 5G مدل ZLT X28 و X28 PRO</h1>

<h2 dir="rtl" align="right">قسمت دهم: از آزمایش روی میز تا انتشار فریمور؛ build، آزمون و ادامه راه</h2>

**نویسنده: علی نادری پاریزی — بازبینی: ۲۰۲۶-۱۱-۱۰**

شروع پروژه درباره بازکردن یه دستگاه بسته بود، اما ادامه‌ش درباره مسئولیت نگهداری شد. دسترسی root یه نقطه شروع خوبه؛ محصول قابل استفاده وقتی شکل می‌گیره که تصویر قابل ساخت باشه، بسته‌ها نسخه مشخص داشته باشن، ارتقا مسیر قابل بررسی داشته باشه و هر ادعا به یه آزمون وصل بشه. این قسمت جمع‌بندی روش توسعه‌ست، نه اعلام پایان پورت.

چیزی که دنبال می‌کنیم یه CPE سلولی با مدیریت آشنای OpenWrt هست: تنظیم شبکه در UCI، رابط LuCI، مالکیت interfaceها در netifd، DHCP و DNS روشن و package manager قابل اعتماد. backend سخت‌افزار هنوز در بخش‌هایی اختصاصیه و Kernel هم نسخه vendor باقی مونده. استانداردکردن مدیریت، مرحله مهمیه؛ رسمی یا mainline شدن کل دستگاه، مرحله دیگه‌ایه.

<h2 dir="rtl" align="right">چطور تجربه شخصی به خروجی قابل تکرار تبدیل شد؟</h2>

در آزمایش اول ممکنه یه فایل رو دستی کپی کنیم تا فرضیه رو بسنجیم. اگر همون فایل بعداً ضروری شد، باید وارد build یا package بشه. وگرنه تصویر تازه، اون «اصلاح کوچک فراموش‌شده» رو نداره و کسی نمی‌فهمه چرا دستگاه توسعه‌دهنده کار می‌کنه ولی نصب تازه شکست می‌خوره.

پروژه با package کردن اجزای x28-* و مصرف همون ipkها در feed و تصویر، این فاصله رو کمتر کرده. x28-base هم dependencyهای ضروری رو معرفی می‌کنه. وجود این package به معنی ناممکن‌شدن خراب‌کردن سیستم نیست؛ صاحب root هنوز می‌تونه dependencyها رو force کنه. هدف اینه که مسیر عادی package manager حقیقت نیازهای سیستم رو نشون بده.

همین الگو درباره تغییر network هم مهمه. تنظیمی که در یه نشست برای آزمایش عوض شده، تا وقتی وارد default یا migration بررسی‌شده نشده، قابلیت clean flash به حساب نمی‌آد. در مستند باید مشخص کنیم اصلاح با دست روی واحد اعمال شده یا از ابتدا داخل تصویر حضور داشته.

<h2 dir="rtl" align="right">نقشه خروجی‌ها؛ کد عمومی، ورودی خصوصی، artifact نهایی</h2>

همه چیز پروژه یه مخزن و یه فایل نیست. بخشی از کدهای مدیریت برد، packageها و CI در مخزن OpenWrt پروژه قرار داره. فلشر و مراحل backup و مونتاژ image به مخزن جدا منتقل شدن. بعضی ورودی‌های vendor هم خصوصی می‌مونن و نباید همراه source مقاله منتشر بشن.

<div dir="rtl" align="center">

| خروجی یا ورودی | نقش | نکته انتشار |
| ---: | ---: | ---: |
| source و packageهای x28-* | منطق قابل بررسی پروژه | تاریخچه و نسخه باید روشن باشه |
| assembly bundle | مجموعه ورودی‌های ساخته‌شده برای مونتاژ تصویر | hash و release مربوط باید همراهش باشه |
| ورودی‌های vendor | اجزای لازم پلتفرم | دسترسی به SDK مساوی اجازه انتشار تمام فایل‌ها نیست |
| feed امضاشده | نصب و update بسته‌ها | index، نسخه و کلید عمومی جزو قرارداد هستن |
| تصویر sysupgrade | ورودی بررسی و ارتقای دستگاه سازگار | قالب، board metadata و امضا لازم دارن |
| dump هر واحد | backup و داده اختصاصی همون دستگاه | فایل عمومی یا تصویر قابل تکثیر نیست |

</div>

داشتن یه دستور build با داشتن ورودی‌های قابل دسترس یکی نیست. اگر build به SDK یا فایل خصوصی نیاز داره، باید همین رو گفت. از اون طرف، خصوصی بودن بعضی ورودی‌ها هم دلیل نمی‌شه منطق باز پروژه، manifest و روش آزمون رو مستند نکنیم. خواننده باید بدونه چه چیزی رو می‌تونه مستقلاً بازسازی کنه و کجا به ورودی سازگار نیاز داره.

<h2 dir="rtl" align="right">پایپ‌لاین ساخت، امضا و فلش رو جدا نگه می‌داریم</h2>

ساخت image یه خروجی تولید می‌کنه. امضا اون خروجی مشخص رو تأیید می‌کنه. فلش روی دستگاه واقعی state رو تغییر می‌ده. اگر این سه مرحله بی‌مرز به هم متصل بشن، اشتباه کوچک در ورودی می‌تونه مستقیم به تغییر دستگاه برسه.

workflow فعلی Image ورودی assembly و rootfs خصوصی رو می‌گیره و خروجی sysupgrade بدون امضا می‌سازه. workflow Sign image hash ورودی و boardهای پشتیبانی‌شده رو دریافت می‌کنه، در محیط انتشار جدا امضا می‌کنه و نتیجه رو با کلید عمومی بررسی می‌کنه. اجرای روی main در کد شرط شده؛ تنظیم reviewer و حفاظت environment هم باید در خود سرویس بررسی بشه، نه از وجود یه اسم در YAML نتیجه گرفته بشه.

در تست ۵۳d، زنجیره امضا به‌صورت محلی و روی دستگاه بررسی شده، ولی برای کل مسیر CI در همون ثبت شاهد سرتاسری ارائه نشده. STATUS به‌روزشده ۱۰ نوامبر، تولید image و خروجی signed در releaseها رو گزارش می‌کنه؛ با این حال، آزمون همون artifact ساخته‌شده در CI روی واحد واقعی رو هنوز جداگانه باز می‌ذاره. این دو سطح شاهد رو یکی نمی‌گیریم.

<h2 dir="rtl" align="right">یه manifest خوب چه چیزهایی رو جواب می‌ده؟</h2>

وقتی کسی از یه خطا گزارش می‌ده، «آخرین نسخه رو دارم» کافی نیست. release، commit، hash تصویر، نسخه Kernel، board، مسیر ساخت و نسخه فلشر می‌تونن نتیجه رو تغییر بدن. همین موضوع درباره feed هم صادقه؛ تعداد packageها ممکنه با یه انتشار تازه عوض بشه.

manifest باید به خروجی مشخص متصل باشه. ثبت hash ورودی‌ها کمک می‌کنه دوباره همون build رو پیدا کنیم. اگر دو خروجی با یه نام و نسخه متفاوتن، این تفاوت باید توضیح داده بشه. reproducible build یعنی برای ورودی و محیط تعریف‌شده به نتیجه یکسان برسیم، نه اینکه هر خروجی‌ای از هر نسخه SDK حتماً byte به byte یکسان باشه.

خود بسته‌بندی هم می‌تونه منبع تفاوت باشه: timestamp، مسیر build، ترتیب فایل و مجوزها. در moduleها ممکنه sectionهای اجرایی برابر باشن ولی مسیر debug متفاوت باشه. گزارش باید بگه مقایسه کل فایل بوده یا فقط sectionهای مشخص؛ هر دو مفیدن ولی ادعای یکسانی ندارن.

<h2 dir="rtl" align="right">آزمون‌ها رو لایه‌لایه می‌چینیم</h2>

اول source و config و dependency بررسی می‌شن. بعد آزمون host می‌تونه parser و guard و انتخاب target رو با فایل جعلی بررسی کنه. container برای نصب package و قرارداد کتابخانه مفیده. QEMU می‌تونه userspace و NAND شبیه‌سازی‌شده رو درگیر کنه. آخر، آزمون دستگاه واقعی لازمه تا رفتار driver، زمان‌بندی، RF و مسیر بوت معلوم بشه.

هیچ‌کدوم جای بقیه رو کامل نمی‌گیره. تست NAND شبیه‌سازی‌شده با Kernel 5.15 ثابت نمی‌کنه dd-nand vendor روی 4.19 همون رفتار رو داره. اجرای daemon در chroot ثابت نمی‌کنه radio روی برد روشن می‌شه. بوت سالم هم به معنی تحمل قطع برق وسط نوشتن misc نیست.

ثبت آزمون ۵۲ همین مرزها رو خوب نشون می‌ده: ۱۶ check در QEMU گذشته، اما محدودیت‌های vendor tool، Kernel و برق واقعی کنار نتیجه نوشته شده. تست ۵۳ بعداً بخشی از همین فاصله رو روی دستگاه پر کرده. این شکل مستندسازی به خواننده اجازه می‌ده بفهمه نتیجه از کجا اومده و هنوز کجا باید محتاط باشه.

<h2 dir="rtl" align="right">clean flash، upgrade و نگه‌داشتن تنظیم‌ها سه آزمونن</h2>

وقتی تصویر تازه از صفر بالا می‌آد، defaultها و تمام dependencyها باید حاضر باشن. وقتی از نسخه قبل ارتقا می‌دیم، کد upgrade مبدأ و تغییرهای format مهم می‌شن. وقتی تنظیم‌ها رو حفظ می‌کنیم، باید ناسازگاری config قدیمی با تصویر جدید رو هم بررسی کنیم.

توی این پروژه، تغییر UUID می‌تونه overlay رو تازه کنه. نتیجه عملی ممکنه شامل کلید host تازه، برگشت بعضی defaultها و حذف اصلاح‌های دستی overlay باشه. در تست‌های ثبت‌شده، sysupgrade با -n بررسی شده؛ حفظ تنظیم با -k هنوز در محدودیت‌هاست. پس نمی‌شه وعده بدیم هر تنظیم قدیمی بعد از ارتقا بدون بررسی باقی می‌مونه.

این موضوع برای کاربر خانگی ملموسه. اگر تنها راه مدیریت دستگاه Wi-Fi باشه و default رادیو عوض بشه، یه تصویر کاملاً بوت‌شده هم ممکنه از دید کاربر «ناپدید» شده باشه. مستند upgrade باید مسیر اتصال بعدی و اثر حفظ یا پاک‌شدن config رو توضیح بده، نه فقط اسم فایل رو بده.

<h2 dir="rtl" align="right">مستند خوب چطور جلوی تکرار یه اشتباه رو می‌گیره؟</h2>

وقتی منبع قدیمی و جدید با هم اختلاف دارن، نباید یکی رو بی‌صدا حذف کنیم. در این مجموعه، چهار مقاله اول یه snapshot تاریخی از مراحل آغازین هستن. فصل‌های تازه بر source فعلی و آزمون‌های تاریخ‌دار بعدی تکیه دارن. مثلاً جمله قدیمی «sysupgrade هنوز وجود نداره» برای همون مرحله درست بود، اما بعد از آزمون ۵۳d توصیف وضعیت همه پروژه نیست.

بهتره کنار هر نتیجه سه چیز ثبت بشه: چه چیزی اجرا شده، روی کدوم واحد و چه چیزی هنوز بررسی نشده. اگر یه نتیجه فقط با گزارش صاحب دستگاه ثبت شده، همون سطح شاهد رو می‌نویسیم. اگر ابزار در repository جابه‌جا شده، مسیر جدید رو معرفی می‌کنیم تا فرمان قدیمی به‌عنوان دستور روز استفاده نشه.

برای همین، منبع اصلی وضعیت روز فقط یه عدد release در README نیست. وقتی جدول قدیمی با test log جدید اختلاف داره، باید تاریخ و کد مرتبط رو کنار هم دید. این مقاله‌ها وعده ثابت درباره همه نسخه‌های آینده نیستن؛ روایت قابل ممیزی از یه مرحله توسعه‌ان.

<h2 dir="rtl" align="right">چه چیزهایی هنوز جلوی عبارت «تمام‌شده» رو می‌گیرن؟</h2>

پشتیبانی رسمی upstream، Kernel نگهداری‌شده جدید، آزمون گسترده چند اپراتور و SIM، سرعت و رفتار clientهای Wi-Fi، SMS و voice در تصویر native، نگه‌داشتن config هنگام upgrade، قطع برق و fallback کامل میان دو slot native هنوز کار مستقل می‌خوان. وجود package یا گزینه رابط کاربری به معنی انجام‌شدن همه این‌ها نیست.

در لایه update فعلی، x28-update-check و اعلان LuCI پیدا کردن نسخه رو انجام می‌دن و x28-upgrade پس از تأیید کاربر دریافت، بررسی و sysupgrade رو به هم وصل می‌کنه. این ابزار خودبه‌خود upgrade نمی‌کنه و حالت فعلیش تنظیم‌ها رو نگه نمی‌داره. آزمون‌های host با ابزارهای جعلی در مخزن هستن، اما رکورد سرتاسری دکمه LuCI روی دستگاه هنوز در وضعیت روز بازه.

OTA بدون حضور کاربر هم باید سیاست نسخه و خطا داشته باشه. قبل از خودکارشدن دانلود و reboot، باید بدونیم دستگاه چطور artifact درست رو انتخاب می‌کنه، چه زمانی مجاز به upgrade هست و اگر برنگشت چه کاری از بیرون ممکنه. ابزار فلش از طریق DL ارزشمنده، اما «کاربر همیشه یه کامپیوتر آماده و کابل دم دست داره» فرض خوبی برای محصول عمومی نیست.

این فهرست برای کم‌ارزش‌کردن پیشرفت نیست؛ دقیقاً نشون می‌ده قدم بعدی کجاست. دسترسی اولیه، تصویر native، شبکه سلولی، بسته‌های امضاشده، ساخت module و چرخه امضاشده A/B هرکدوم مسئله واقعی‌ای رو حل کردن. حالا باید همون کیفیت رو به مسیر نگهداری و آزمون خطا برسونیم.

<h2 dir="rtl" align="right">تشکر، مشارکت و ادامه مجموعه</h2>

از Tozed بابت در اختیار گذاشتن SDK تشکر می‌کنم. این دسترسی برای شناخت دقیق‌تر پلتفرم و ساخت اجزای سازگار ارزشمند بود. از پروژه‌های OpenWrt، Linux و پژوهش‌های قبلی X28 هم استفاده کردیم؛ منابع هر بخش جدا آورده شدن تا سهم ابزار عمومی، کد پروژه و backend vendor مشخص بمونه. این فریمور توسعه مستقل ماست و این تشکر، ادعای پشتیبانی رسمی شرکت از اون نیست.

برای مشارکت، یه گزارش قابل تکرار از یه جدول سبز بدون شاهد مفیدتره. مدل و revision پالایش‌شده، نسخه، سؤال آزمون، مسیر اتصال، نتیجه و محدودیت‌ها رو ثبت کنیم. dump کامل، کلید، شناسه SIM و calibration رو عمومی نفرستیم. اگر قرار باشه روی برد تازه آزمایش کنیم، اول مسیر backup و برگشت رو روشن کنیم.

داستان از یه دستگاه قفل‌شده شروع شد، ولی حالا موضوع فقط بازکردن قفل نیست. داریم یاد می‌گیریم چطور یه پلتفرم واقعی رو بشناسیم، خروجی قابل ساخت منتشر کنیم و به کاربر امکان مدیریت معمول OpenWrt بدیم. ادامه این مجموعه هم باید با همین معیار جلو بره: هر قابلیت تازه، یه مسئله مشخص، یه پیاده‌سازی قابل بررسی و یه نتیجه مستند.
