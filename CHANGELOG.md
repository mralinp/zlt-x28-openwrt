# Changelog

A merge to `main` that changes shippable files is a release; docs-only and CI-only merges are not (see [docs/WORKFLOW.md](docs/WORKFLOW.md)), so this file has two parts: the
milestones below, written by hand, and the full per-release list at the bottom, generated by
`python3 scripts/changelog.py`. Versions are pre-releases (0.x) until the first stable image.

## Unreleased

The release for this was still building when this was written; it moves under a milestone once tagged.

- `x28-upgrade` (CLI) and an *Upgrade now* button on that notice: download the newest signed image, check its `.sha256`, `sysupgrade -T`, then `sysupgrade -n` to the other slot (#515).

## Milestones

### Sysupgrade, signed images and the image built in CI: v0.68.1 – v0.77.0 (2026-11-08 → 2026-11-09)

The image can now replace itself, and a release carries a flashable image. Newest first:

- **Update notice** (v0.77.0): LuCI Status > Overview shows a notice with links when a newer release carries a signed sysupgrade image
  (`x28-update`, read-only check cached in `/tmp`); the release stamps its version into the image as `/etc/x28-release` (#511).
- **PRO Wi-Fi** (v0.76.1): `x28-wifi-l1` writes the two-card `l1profile` when it finds two Wi-Fi chips (#513).
- **Sysupgrade writes the other slot** (v0.76.0): every upgrade writes the slot that is not running, verifies it, then gives it the
  boot priority; the running slot stays the fall-back. On a unit with stock on B, the first upgrade replaces stock (#509).
  Images up to v0.75.0 still write in place unless told otherwise, because an upgrade runs the old image's `platform.sh`.
- **The image is built in CI** (v0.75.0): the Image workflow builds the general native image from the release's assembly and the
  private stock rootfs and attaches `x28-native-image.tar.gz` (for the flasher) and `x28-sysupgrade-<version>-unsigned.tar`;
  Sign image, approved by the owner, adds the signed `x28-sysupgrade-<version>.tar` and its `.sha256`. All are in `SHA256SUMS` (#254, #476).
- **5G in the Carrier tab** (v0.73.2 – v0.74.3): 5G (EN-DC) state and NR signal from `x28-nrband signal`; the tab survives reopening
  the interface dialog; `/etc/board.json` describes the MT7531AE so LuCI stops warning (#492).
- **Signed images** (v0.71 – v0.73.1): `image_sign.sh` signs with `fwtool` and `ucert`, a separate signer key certified by the offline
  feed key; with `ucert` on the router only a signed image passes. Proven on the unit with an A to B to A cycle (test 53d, #476).
- **Sysupgrade** (v0.70.0 – v0.70.4): `package/x28-sysupgrade` (`/lib/upgrade/platform.sh`, the `misc` writer, the `ubiformat` write and the
  volume verify), host-tested, run on simulated NAND in QEMU (test 52) and on the unit: identical image, changed image and native
  slot B (tests 53 to 53c). The release bundle carries its files. Design: `docs/research/sysupgrade-design.md` (#154, #457, #465).
- **Running slot, not slot A** (v0.68.2 – v0.69.0): `x28-kmods`, `x28-bootok` and the `user_data` guard read the running slot's tries
  byte, so a native slot B works (#451, #452).
- **Docs and tests**: the hardware specification `docs/MODULES.md` (USB-C, the Ethernet sockets, the switch ports); recovery is the
  flasher over DL mode, not a recovery slot (#302); test 50 (package rollback needs a downloaded ipk) and test 51 (two units on
  v0.68.1); docs aligned with v0.77 (#479).

### The package feed, the x28-* packages and the assembly bundle: v0.57.3 – v0.68.0 (2026-11-07 → 2026-11-08)

The image and the signed `opkg` feed now come from one set of packages. In order of arrival, newest first (the feed stood at 224 packages in v0.68.0):
- Test 49: the feed with the x28-* packages is live (222 packages) and two units run the packaged image (#421, #423).
- `x28-base` requires `x28-switch` and `x28-nrband` (release 2); the next feed revision (224 packages) is pinned, and the band tool ipk is pinned like the module ipks (#436).
- `x28-switch` is a package and a member of `x28-base`; `vendor_ipset.py --nrband` adds `x28-nrband` to a feed; the band tool is built reproducibly and stripped. The feed revision and `x28-base` dependency on `x28-nrband` follow (#436).
- The next feed revision (222 packages, with the x28-* packages and `x28-base`) is pinned in `feed_release.py` and listed for review; it checks equal to the release ipks. Not yet signed or published (#423).
- Docs: the package model (required, preinstalled-optional, on demand), the update policy and rollback (#422).
- One set of ipks per release for the image and the signed feed (#419): CI builds the x28-* packages, the module ipks come from the
  feed release by pinned hash, `tools/build/release_check.py compare` proves a feed revision holds the same bytes, and the
  `kmods-4.19.205` release is retired.
- Releases publish one `x28-assembly-vX.Y.Z.tar.gz` (userspace, package files, the eight kernel modules, extra packages)
  instead of loose userspace, manifest and overlay assets; the modules are published as release `kmods-4.19.205`.
  The x28-flasher must switch to the bundle (#352).
- Docs audited and aligned with v0.57; changelog milestone for v0.39 – v0.57 (#359).
- The X28 opkg feed is now `feed-3` on a stable URL (`https://github.com/mralinp/zlt-x28-openwrt/releases/latest/download`): 213 signed packages, including 28 that carry kernel modules built for the vendor kernel and the `x28-kmods` loader, which reads a list from each module package (WireGuard and TPROXY, traffic shaping and SQM, `veth`, `macvlan`, `bonding`, `nbd`, ChaCha20-Poly1305, and more). `x28-kmods` loads 51 modules at boot. The flasher writes the new URL. See `docs/PACKAGE-FEED.md` (#394 to #398).
- Firmware releases are created with `--latest=false`, so the feed release stays the repository's "latest" (#406).
- Docs audited and aligned with the package feed and v0.62: stale feed statements fixed, the TESTING numbering corrected (sections 45 and 46), the research notes listed in `docs/README.md`.

### Carrier control, flashing other units and the flasher: v0.39 – v0.57 (2026-11-03 → 2026-11-06)

The image gained real carrier control, and the flashing tools grew into a separate product. In order of arrival:

- **Wi-Fi** (v0.38.6 – v0.39.2): one network per band (the guest network is gone), a WPS push button opened by the
  router's button, and notes on the reset and WPS buttons.
- **x28-flasher** (v0.40 – v0.53, then moved out in v0.54): a guided single binary (PyInstaller, built for macOS arm64
  and Linux) with a menu, UART logging, Backup, Build and an Auto pilot from backup to write. The guarded tools run
  inside the frozen binary. The Rust `x28flash` tool was dropped. The project was relicensed from MIT to GPL-3.0-or-later.
- **Other units** (v0.50 – v0.54): `rootfs_a` pins come from the unit's own verified backup, `--no-ssh` and `--no-uart`
  paths, and `misc_entry` selects slot A on a unit's own `misc` record over USB. Second unit (X28 PRO, stock 8.6.8)
  analysed in `docs/research/flash-other-units.md`. SSH was later gained on stock 8.6.8, valid to 8.6.28 (#357).
- **Image** (v0.49.1, v0.51): Passwall2's stop link so LuCI Save & Apply starts it; root can log in over SSH with a
  password as well as a key.
- **Carrier** (v0.54 – v0.57): attach APN sync and a roaming option (default off), a bounded data call that recovers
  the radio, operator selection with a network scan, 4G and 5G band lock, a strict cell lock, and a LuCI Carrier tab
  on the `x28_mipc` protocol with modem status (rpcd ACL fixed in v0.57.2).
- **Release** (v0.43, v0.55): releases happen only when shippable files change; the `x28-overlay` asset is published
  for x28-flasher, which now owns image assembly in its own repository.
- **Docs** (v0.49.1, v0.56): an illustrated article series, and the README states the tested firmware.

### VPNs, Passwall2 and the package feed: v0.30 – v0.38 (2026-10-31 → 2026-11-02)

The native image grew from a bare router into one that carries VPNs and a transparent proxy. In order of arrival:

- **Wi-Fi** (v0.30.0, v0.34.2 – v0.34.3): a country setting and a scan for `mt_wifi`; a clean flash now starts with
  Wi-Fi off and a random key, open first-boot defaults restored, and `iwinfo info` no longer crashes on `apcli0`.
- **Package feed** (v0.31 – v0.34.1): a conservative vendor-kernel compatibility feed, the observed vendor `ipset`
  subset, and a signed X28 opkg feed with its key shipped in the image (the vendor kernel's MODVERSIONS means the
  official kmods do not load, so kmods are stubs or built here).
- **VPNs and Passwall2** (v0.35 – v0.38): WireGuard, OpenVPN, `dnsmasq-full` with `ipset`, the TPROXY modules and
  Passwall2 with HTTPS LuCI in every image; our kernel-module sources live in the repo; the LAN kill switch lets
  direct ICMP and Passwall2's own direct destinations through.
- **Tooling and research** (v0.30.1 – v0.30.9, v0.36 – v0.37): hardware, RAM and flash notes, a root filesystem and
  device tree, LK boot-authentication mapping, the verified UART pinout, a slot A soak record, and a read-only
  `x28flash` Rust USB tool.
- **Measured** (v0.30.4, v0.34.4 – v0.34.5, v0.38.2): VPN speed and CPU limits on the router, OpenVPN OpenSSL speed
  and Passwall2 throughput from a LAN client.

### Native image on slot A: v0.12 – v0.22 (2026-10-28 → 2026-10-29)

The first native image was written to `rootfs_a` and booted on a real unit. In order of arrival:

- **Boot and management** (v0.4 – v0.11): private staging of the rootfs with the stock modules, a guarded first-boot
  management profile (key-only SSH, physical console shell), UBI packaging, the MT7531 switch table, and a guard
  (`ab_guard`) that refuses any image whose boot path can write flash or sync the other slot.
- **Flash tooling** (v0.2 – v0.21): bounded, receipt-sequenced sessions for `rootfs_a`, with hash-pinned originals,
  neighbour guards read before and after every write, typed approval phrases, and restore re-entry. Base mode
  (v0.21) lets a new image replace the one already on slot A. Proven on hardware for `rootfs_a` and `rootfs_sig_a`.
- **Networking** (v0.14 – v0.16): all four LAN sockets bridged, `dnsmasq` DHCP and DNS, IPv6 on the LAN; the
  `x28_mipc` cellular protocol gained IPv4/IPv6/IPv4v6 and the APN read from the SIM.
- **Wi-Fi and LEDs** (v0.13, v0.17): native MT7915 dual-band Wi-Fi through a netifd handler for the vendor `mt_wifi`
  driver, and the front panel LEDs driven from radio, signal and WAN state.
- **Everything at boot** (v0.19 – v0.22): the modem stack, `rpcd`, `uhttpd`, the firewall, Wi-Fi defaults and the APN
  database start by themselves; the overlay now persists (`S95done`); root starts with an empty password like stock
  OpenWrt; SSH moved to port 22; `x28-bootok` resets the A/B boot-tries byte after every good boot.
- **Verified on the unit** (2026-10-29): 5G data with internet, LuCI login, NAT, both Wi-Fi radios up, settings and
  host keys surviving reboots, `misc` tries returning to 0 after a boot, about 40 °C idle on the SoC.

Known limits at this point: slot A is not marked successful (success byte stays 0 on purpose, so the preloader's
fall-back to stock B remains); the download-agent block write to `misc` was never acknowledged (twice), so `misc`
is changed only live with the stock `dd-nand` method; Wi-Fi throughput and client behaviour are untested.

### Recovery and boot-flow research: v0.1.5 – v0.12 (2026-10-23 → 2026-10-29)

UART console, the A/B slot map, the rootfs signature check (traced to a panic halt in LK, with no secure boot and no
content check found), the first identical-byte and changed-page USB writes on an inactive slot, and the attempt to
read the preloader's slot-selection logic (inconclusive; see `docs/research/`).

### Foundation: v0.1.0 (2026-10-23)

Verified NAND backup of all 51 partitions, USB recovery over the MediaTek download agent, firmware inventory
(kernel config, modules, vendor packages, ABI), the CI build of the OpenWrt 23.05.5 userspace (fw3 +
iptables-legacy), a QEMU boot test on every build, the reboot-surviving temperature logger, and automatic
releases.
